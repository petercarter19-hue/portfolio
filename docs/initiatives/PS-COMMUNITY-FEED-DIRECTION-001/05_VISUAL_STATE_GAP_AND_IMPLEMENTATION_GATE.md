# Community Feed visual-state gap and implementation gate

## 1. Current result

Pete locked a strong six-screen primary journey on 2026-07-31:

1. desktop Feed;
2. desktop selected Motion contribution;
3. desktop complete vertical conversation;
4. mobile Feed;
5. mobile Catch up and Spark sheet; and
6. mobile selected Motion contribution.

That is enough to lock the product's central composition and interaction
model. It is not enough to claim a complete V1 visual system or authorize
runtime implementation under the Owner Visual Integrity Standard.

Pete approved SAR-01 through SAR-06 on 2026-07-31 inside this package. That
approval authorizes a later shared-document activation and bounded ChatGPT
visual-completion round; it does not itself amend shared authority or permit
runtime work. The architecture has since been reviewed and refined against all
six screens in documents 04 and 07.

## 2. Required ChatGPT visual-completion boards

ChatGPT remains the sole creator of new or materially revised production-intent
visual authority. The next visual round must use the six locked files as exact
reference authority and fill only the missing states below. Pete must inspect
and lock the resulting exact files before runtime begins.

### A. Feed request and availability states

- initial desktop and mobile loading/skeleton;
- partial module loading without collapsing Feed geometry;
- full Feed unavailable with retry;
- post-local Replies & updates unavailable while the post remains usable; and
- stale/new-content notice that does not silently move the caught-up boundary.

### B. Empty and completion states

- true new-member Community empty state with no fake people or activity;
- Following/no-relationship empty state if Following is adopted;
- filtered-result empty state;
- desktop and mobile caught-up state with the final locked actions; and
- no eligible Replies & updates state, where the shelf is absent rather than
  shown empty.

The completed set must also resolve the retained `Following` / `Recent` mode
and `Questions` filter inventory: lock the exact control/default, or record an
owner amendment that defers the absent modes rather than letting runtime infer
them.

### C. Composer and publication states

- focused desktop and mobile composer;
- explicit audience selection and confirmation;
- exact response-posture treatment and confirmation that it is display-only,
  or separately approved capability semantics;
- Spark attached, changed, and removed;
- image, gallery, video, and document attachment preparation;
- upload processing, failure, retry, and removal;
- recoverable submission failure with text preserved; and
- successful publication without an invented activity claim.

The recommended first runtime slice creates Community-native posts only and
derives conversation labels without a subject input. If Pete expands that
slice to Slate-projected creation or an author-supplied subject, this state set
must first add source selection, pinned-revision preview, effective-audience
confirmation, source-unavailable/revoked recovery, subject entry, validation,
and editing states.

### D. Conversation and contribution edge states

- mobile full `View all Replies & Updates` traditional conversation;
- loading and retry inside selected-contribution and full-conversation views;
- long post, long contribution, long member name, long filename, and large-text
  clamping/expansion;
- multiple attachments using first item plus `+N` in Motion and full media in
  focus;
- image, gallery, video, and combined-media Motion contribution;
- edited, deleted, moderation-held, blocked, revoked, and permission-denied
  contribution truth; and
- a long conversation with paginated vertical loading.

### E. Rail and mobile-function states

- left return rail with fewer/zero Since you were here items;
- no resumable Continue the conversation item;
- Spark unavailable or changed;
- Community Pulse and Active Questions empty/unavailable states;
- the approved mobile destination for Community Pulse and Active Questions,
  if they are required on mobile; and
- Catch up sheet with long content and partial failure.

### F. Accessibility, reflow, and theme evidence

- visible keyboard focus throughout Feed, shelf, overlays, and sheet;
- 200% browser zoom/reflow while preserving a single horizontal Motion row;
- reduced-motion behavior;
- phone landscape and large dynamic text;
- desktop narrow/wide boundaries and rail collapse behavior; and
- dark-theme direction or an explicit owner decision that the first authorized
  Community slice is light-theme only. Existing site theme behavior must not be
  broken silently.

### G. Messaging truth state

The approved mockups contain `Message`, but messaging is not currently
authorized as a Community capability. Before Feed implementation, lock one
truthful pre-messaging treatment:

- hidden until available; or
- visibly disabled/unavailable with honest explanation.

The sent-state visual (`Message sent`, then collapse/close) belongs to the
future messaging package, not this initial Feed implementation.

### H. Shell, search, and signed-out truth

The primary lock visibly includes `Search Community`, `New post`, and member
shell controls. Before runtime, the completed state set must:

- preserve current `Community` → `/the-slate`, `Feed`, and `The Break` route
  authority rather than copy illustrative mockup chrome;
- treat `New post` and mobile `+` as the same composer;
- either add Community-local search to the approved inventory and lock its
  loading, empty, failure, permission, result, and mobile states, or lock a
  truthful removal/deferment;
- lock a public payload-free signed-out/sign-in state because the current
  `/the-slate` shell is publicly reachable while real Community data will be
  protected; and
- identify every exact CSS comparison viewport, DPR, route, scroll position,
  shell variant, overlay/sheet state, rail state, composer variant, and initial
  focus represented by the durable files.

### I. Visible actions and subordinate states

The six primary screens show controls whose complete outcomes are not yet
locked. The visual-completion round must either lock each retained outcome or
explicitly defer/hide the control in the first runtime slice:

- Respond tray with all five approved intentions, current selection,
  replacement/removal, loading, retryable failure, keyboard/focus, and mobile
  behavior;
- post and contribution ellipsis menus for author versus ordinary viewer,
  including edit/remove/report/mute/block/copy-link availability;
- synchronized post/contribution Save controls, saved state, in-flight state,
  and recoverable failure;
- contribution composer target, attachment, emoji, and conditional mention
  treatment;
- Feed file `Open`, separate download, image/gallery viewing or explicit
  noninteractive treatment, processing, revoked, and unavailable states;
- personal expanded activity and `Pick this back up`;
- Pulse `See all activity` and `See all questions` as bounded subordinate
  states or explicit removal;
- `Revisit saved posts`, `See what changed`, and `Ask the community` from the
  caught-up ending without establishing a third Community view;
- separately named access to a pinned Slate source if Slate-projected posts are
  displayed, never overloading selected-contribution `View original`; and
- exact source/profile link unavailable behavior.

Every subordinate state must preserve the current two-view route model,
authorize before snippets/counts/media, and restore its invoking Feed, shelf,
sheet, scroll, and focus state.

## 3. Current v3 authority reconciliation

Pete approved the narrow reconciliation proposal in document 06. The v3.0
lean control plane, adopted later on 2026-07-31, removed the historical shared
site-rule and Context Rail collisions on which the original five-document
activation plan was based. The package decisions below remain controlling
feature direction:

1. **Community Post truth:** approve the first-class Community Post and
   contribution model without Journal as a launch dependency.
2. **Right rail:** Community Pulse and Active Questions are package-local
   Community modules, not ranking or popularity furniture.
3. **Left rail:** authorize the accepted Community-local return rail without
   declaring it to be a new global navigation layer or the shared Context Rail.
4. **Break boundary:** preserve the separate Break destination while recording
   that distributed Break cards are not part of the first locked Feed.
5. **Route/shell:** preserve the actual Community route and navigation labels
   without copying illustrative mockup chrome.

Constitution v3.0 rule 7 currently says Community connects selected output. A
separate Protected documentation change should decide whether to clarify that
durable boundary so a member may also deliberately publish Community-native
social speech whose source of truth remains the Community conversation. It may
not weaken private-before-public, create a second Slate fact store, or turn
Community speech into canonical Journal/Slate truth. Roadmap v3.0, the lean
site rules, and the current control plane need no change for the other four
subjects. Archived `CURRENT_STATE.md` and `ACTIVE_INITIATIVES.md` must not be
updated.

## 4. Dedicated runtime package required afterward

After shared authority and visual completeness pass, create a new runtime
initiative rather than turning this direction package into an implementation
branch. It must name:

- exact manager and one active writer;
- authoritative base SHA and collision check;
- route, template, CSS, JavaScript, service, schema, test, and migration scope;
- authorization, audience, moderation, attachment, privacy, and rollback
  contracts;
- direct-to-quarantine upload reservation/finalization/callback ownership and
  revocable preview/download delivery;
- mandatory retirement or immutable fixture-only isolation of the legacy
  mutable People & Interests API before real-member cutover;
- generic multi-member fixtures;
- exact visual comparison viewports and state matrix;
- homepage/shared-shell parity requirements;
- native tablet responsiveness and private/no-store coverage for every new
  Community blueprint response, including early errors;
- accessibility and performance budgets;
- independent review triggers; and
- merge, deployment, production smoke, and cleanup gates.
