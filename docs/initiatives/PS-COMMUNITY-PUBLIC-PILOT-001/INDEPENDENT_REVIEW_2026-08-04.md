## Verdict: **Fail**

Two P0 defects. The first is proven end-to-end at runtime, not inferred: with
`PEERSLATE_COMMUNITY_PUBLIC_PILOT_ENABLED=true`, the seven new retention and restore
stored procedures are absent from `services/database_service.ALLOWED_PROCEDURES`, so
`execute_procedure` raises `ValueError` — which is *not* a `DatabaseServiceError` and is
therefore not caught by the `sweep_*_best_effort` handlers whose stated purpose is to
never fail a member request. Because the sweep is invoked from an **app-wide**
`@app.before_request`, enabling the flag returns **HTTP 500 on every route on the site**,
including `/`. I reproduced this: `GET /` → 500 and `GET /the-slate` → 500. The same gap
independently makes the entire Recently-deleted and restore feature non-functional. The
second P0 is that the 30-day purge sets `body = N''`, which violates the pre-existing
`CK_community_posts_body`/`CK_community_contributions_body` check constraints
(`LEN(body) BETWEEN 1 AND …`), so the approved permanent-erasure job cannot succeed even
after the first P0 is fixed. Neither defect is reachable by any test in the branch: the
2,062-test suite passes because the `before_request` is skipped under `TESTING`, the
retention tests mock the database and string-match the SQL text, and the disposable SQL
proof only applies and rolls back the migrations without ever executing a purge or
restore procedure. Compounding this, `templates/community_pilot_policy.html` publishes
retention promises ("permanently erased", "stays recoverable by you for 30 days in
Recently deleted") that the shipped code does not perform — a direct violation of the
always-on truthfulness invariant in `AGENTS.md`. The architecture, authorization model,
and flag-off archiving are sound; the defects are concentrated in the newest tranche
(retention, restore, policy text) and are individually fixable.

## What I verified and found correct

Coverage, so the reader knows where I actually looked rather than only where I found problems.

- **Authorization and cross-user data (brief item 1) — correct.** Every Community procedure resolves the actor server-side via `DECLARE @UserId int=(SELECT id FROM dbo.app_users WHERE user_key=@UserKey AND active=1 AND account_status=N'active')` and scopes mutations by `author_user_id=@UserId` or `uploader_user_id=@UserId`. I read all three new procedures (`usp_RestorePublicCommunityPost`, `usp_RestorePublicCommunityContribution`, `usp_ListRestorableCommunityForOwner`) plus `usp_SetCommunityLegalHold` and all eleven media procedures. **I found no procedure that can read, act on, or reveal another member's record.** A `NULL` `@UserId` degrades to a predicate that matches nothing rather than to an unscoped statement. `community_api.py` never accepts a user key from the client — I grepped for it; every `user_key` argument originates from `identity.user_key` behind `_owner_identity()`/`get_optional_identity()`. `usp_RestorePublicCommunityPost` returns a neutral `not_found` for another member's key, and `community_restore_service._restore` maps it to a generic error, so existence is not probeable. `community_recently_deleted` returns 404 rather than 403 for the same reason.
- **Restore boundaries (brief item 3) — correct apart from F3/F11/F12.** Purged, held, expired, and other-owner records are all correctly refused, each on an explicit branch. The `@@TRANCOUNT` / `SAVE TRANSACTION` nesting pattern matches the delete procedures it mirrors, and the `WITH(UPDLOCK,HOLDLOCK)` read-then-update is race-safe. Restoring a contribution under a still-deleted parent is refused (`parent_unavailable`), so no unreachable or leaking state is created. Idempotency is consistent with the delete path (`existing` on a live record). Restore deliberately does not resurrect other members' responses and saves, matching the approved decision.
- **Archiving the old Community (brief item 4) — correct; no flag-off regression found.** I checked this at runtime as well as by reading. Every retirement is behind `_retired_by_community_pilot()` or an explicit flag test, and the `base.html` search index uses `{% if not community_public_pilot_enabled %}` such that the flag-off render is byte-identical to `origin/main` and the flag-on render is still valid JSON in both the owner and public branches. The new `before_request` is a no-op when the flag is off. I confirmed `slate_feed()` and `the_slate_people_interests()` are pure redirects and that `the_slate_people_interests.html` — which calls `url_for('people_interests_api…')` and would raise `BuildError` under the conditional blueprint registration — is never rendered by any route. The blueprint registration reorder is safe: blueprint-scoped `before_request` hooks only fire for their own blueprint, and no URL rules collide. With the flag on I confirmed `/the-slate/my-slate`, `/the-slate/pulse`, `/the-slate/break` → 302 and `/api/slate-feed` → 404.
- **Scheduler safety (brief item 5) — partly correct.** The `Lock(blocking=False)` skip-rather-than-queue behaviour is right, the cadence arithmetic is right, and the procedures are genuinely safe to run concurrently across workers: `UPDLOCK, READPAST` means two workers claim disjoint rows and a crashed worker leaves nothing locked. The purge cannot touch live content — every predicate requires `deleted_at_utc IS NOT NULL`. The flag *is* checked before the sweep runs, so a flag-off deployment never calls the procedures. What is wrong is the exception type (F1), the inline-blocking docstring and cold-start behaviour (F13), and the unbounded revision deletes (F7). Notably, the sibling media worker is correctly defensive: I confirmed `community_media_maintenance` swallows its `DatabaseServiceError` and returns 200 when the database is unreachable — the retention path is uniquely broken, which is what makes F1 an oversight rather than a design choice.
- **Truthfulness (brief item 6) — the numbers match, the behaviour does not.** Every duration in `community_pilot_policy.html` matches `services/community_retention_service.py` (30/90/30/90) and the SQL defaults, and matches `APPROVED_RETENTION_AND_DELETION_DECISION.md`. "Community searches are not stored" is true — I read `usp_SearchPublicCommunity` and it performs no audit or outbox insert, and the route does not log the query. The AI-truth paragraph matches the voice implementation. The failures are F4 (erasure and recoverability promised but not performed), F6 (reply drafts), and F9 (the one-hour attachment promise).
- **Draft expiry (brief item 7) — correct for the two implemented surfaces; cannot wrongly destroy content.** `DRAFT_IDLE_LIMIT_MS` is exactly 30 days. `draftHasExpired` fails *closed* in the safe direction: `typeof value.saved_at !== 'number'` returns `false`, so an undated or corrupted draft is preserved rather than discarded, and a backwards clock jump produces a negative delta and cannot expire a live draft. `readPrimaryCommentDraft` explicitly preserves pre-upgrade plain-string drafts. `saved_at` is refreshed on every save, so the clock is genuinely "30 days without an edit" as published. Expiry is evaluated on read only — the bytes remain on the device until the next visit — which I consider a defensible reading of the promise but worth stating plainly. The gap is F6.
- **Also checked and found sound:** the same-origin write gate in `community_api.protect_public_pilot` (custom header + `Origin` + `Sec-Fetch-Site` + JSON enforcement); the absence of a CSRF token on the restore form, which is consistent with the application-wide convention — the app has no `CSRFProtect` anywhere and relies on `SESSION_COOKIE_SAMESITE='Lax'`, which does suppress cookies on cross-site POST, so this is not a new weakness; the `X-Robots-Tag`/`Cache-Control: private, no-store` headers on all Community responses; the media state machine's `CK_community_media_clean_ready` invariant and the claim-token protocol on cleanup completion; the fact that `media_state='ready'` and `removed_at_utc IS NOT NULL` cannot coexist through any code path, so the two read procedures that filter only on `media_state` (`…_community.sql:1064`, search) do not leak removed attachments; and the rollback's refusal to proceed while any legal hold exists.
- **Test baseline reproduced.** Full suite from the worktree with the project venv: **2,062 passed, 8 skipped, 2,387 subtests passed, 1 failed** — the single failure is the known Windows-only `test_private_environment_file_has_owner_only_permissions` (POSIX `chmod`, passes on Linux CI). This matches the author's stated baseline exactly. The six Community retention/restore/archiving suites pass on their own (59 passed, 1 skipped).

## What I could not verify, and why

- **F2 is a static finding, not a runtime-proven one.** I did not have a SQL Server instance available and the review is read-only, so I did not run the Docker-based disposable proof or execute `usp_PurgeCommunityContent`. The finding rests on a direct reading of `CK_community_posts_body CHECK (LEN(body) BETWEEN 1 AND 4000)` against `SET body = N''`, where `LEN(N'') = 0` and a CHECK constraint rejects a row whose predicate is FALSE. I regard this as high confidence but it should be confirmed by executing the procedure against seeded rows — which is itself the recommended fix to the proof's coverage gap.
- **The cited SQL proof runs 422/424/429/439 are not verifiable from this branch.** The committed evidence under `evidence/2026-08-02-disposable-sql-proof/` is runs **339** and **344** only. I could not inspect the artefacts for the runs named in the task brief and in `APPROVED_RETENTION_AND_DELETION_DECISION.md:110` ("Proven at run 429"). Independent of that, I established by reading `scripts/run_community_disposable_sql_proof.py` that the proof's stages are `preflight`, `empty_forward`, `forward_idempotency`, `two_owner_verifier`, `empty_rollback`, `populated_rollback_refusal`, `cleanup` — it applies and rolls back the migrations and publishes one post, and **contains no `EXEC` of any purge or restore procedure**. So whatever those runs show, they do not constitute proof that the retention or restore behaviour works.
- **Production Azure configuration claims are unverified.** The policy's "encrypted database backups, which are kept for 7 days", the Blob soft-delete window, and the assertions in `RETENTION_PRODUCTION_CONFIGURATION_EVIDENCE_2026-08-04.md` describe live Azure settings. I did not query Azure (read-only review, and doing so was out of scope). These need owner or operator confirmation against the actual subscription.
- **No browser-based verification.** Pete has already given visual acceptance and I was explicitly not reviewing aesthetics, so I did not run the preview scripts or capture screenshots. My findings on `community-v1.js` and the two templates come from reading the source, not from exercising the UI. F3's user-visible symptom (a restored post rendering without its attachments) is derived from the SQL read filters rather than observed.
- **Multi-worker behaviour is reasoned, not measured.** F13's per-process scheduling and the concurrency safety of `UPDLOCK, READPAST` were assessed by reading; I did not run a concurrent load test.
