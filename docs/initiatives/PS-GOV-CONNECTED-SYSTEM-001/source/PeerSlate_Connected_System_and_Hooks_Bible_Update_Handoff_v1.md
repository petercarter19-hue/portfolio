# 4. Executive product decision

The connected-system strategy has three reinforcing layers:

1. **Structural continuity:** every major room reveals what it is, where its material came from, how it relates to the Slate, and the best next move.
2. **Canonical continuity:** sources, confirmed facts, relationships, interpretations, projections, and outcomes remain distinct but traceable.
3. **Temporal continuity:** PeerSlate helps the member return to earlier work, see change, continue an unfinished thread, and take a small next action without pressure.

The new constitutional language should define PeerSlate as a system of **focused rooms connected by a visible spine**, not a single blended dashboard and not isolated page islands.

## 5.3 Product boundaries

Add to **PeerSlate is**:

- A product where a small contribution can compound into future recall, preparation, expression, and decision support.

Add to **PeerSlate is not**:

- Not a collection of generic "related content" rails or promotional cross-links.
- Not a habit game that treats absence as failure.
- Not an emotional-diagnosis system derived from voice, behavior, or inferred mood.

## 5.4 One connected Slate

Add a subsection titled **The connected-system spine**:

> One connected Slate is not achieved only by sharing a database. The experience must make the relationship visible. Original sources enter a reviewable pipeline; confirmed records connect through governed relationships and exact-version placements; focused rooms receive only authorized context; member actions create reviewable projections or outcomes; and useful history returns through finite Home, Replay, resurfacing, and preparation. Each layer remains separately governed so connection never erases truth boundaries.

Add a subsection titled **Relationship before promotion**:

> Cross-room movement must explain why another room matters in the member's current context. PeerSlate should prefer "Practice telling this result," "See how this line was earned," or "Return to the Moment behind this answer" over generic "Explore more" links. Relationship-rich cues are part of the product model, not marketing decoration.

## 5.5 Experience model and information architecture

Add a locked subsection titled **The connected-room contract**:

Every primary room must answer, at the appropriate depth:

1. What is this room helping me do?
2. Whose space and which audience or truth state am I in?
3. Where did this material come from?
4. How does it relate to the larger Slate?
5. What is the one best safe next move?

The contract must support the same grammar with different authorized payloads:

- **Public or permissioned mode:** approved public relationships, approved projections, public-safe source context, and truthful current capability.
- **Owner mode:** private source relationships, prior work, drafts, outcomes, goals, Projects, Replay, and exact audience preview.

No private information may be retrieved and hidden in the browser. The server must authorize the relationship before it is returned.

Add a subsection titled **Focused but not orphaned**:

> Task rooms such as Studio may reduce chrome while the member is answering, recording, or reviewing. Orientation and continuation should appear at natural boundaries, especially before the task and after meaningful progress, rather than interrupting the task. The default connective budget is one primary bridge and no more than two secondary paths.

Add a subsection titled **The temporal spine**:

> PeerSlate connects not only across rooms but across time. When sufficient confirmed history exists, a room may reveal an earlier related Moment, a meaningful change, an unfinished thread, or a future revisit. Temporal cues must be source-linked, dismissible, non-diagnostic, and free of guilt.

## 5.6 Signature experiences and product ecosystem

Add a subsection titled **Connected-room patterns** and preserve the following as canonical experience patterns, not top-level destinations:

- **Slate Spine:** compact orientation showing room role, one or two meaningful relationships, and one primary next action.
- **Backstory Drawer:** public-safe path from a selected Resume claim or Work highlight to the context, impact, related Story or Project, and optional practice route.
- **Studio Return Ticket:** post-review continuation that reconnects practice to approved support, a related question, a saved lesson, or a later retry appropriate to the current mode.
- **Then and Now:** source-linked temporal comparison showing change, recurrence, or continuity without declaring identity or capability as fact.
- **Focus Theme:** a private, optional season-level intention that may tune prompts, resurfacing, Replay, and preparation without becoming a new destination.
- **Progress Keepsake:** a member-selected reference to a meaningful quote, clip, before-and-now pair, Replay item, or confirmed projection. It is not a trophy, a duplicate record, or a popularity object.

Add a subsection titled **The return-value engine**:

> PeerSlate's enduring return loop should be built from a tiny worthwhile contribution, immediate truthful payoff, later memory or progress value, and one gentle continuation. The preferred pattern is: small check-in or Capture -> reviewable value -> finite resurfacing or Replay -> personalized source-linked prompt -> optional next action. Returning after absence is treated as continuation, not failure.

# 6. Architecture map and logical contracts

## 6.1 High-level architecture

The architecture map must show a single compounding loop rather than separate feature trees:

1. **Original source layer:** voice, text, photo, file, imported context.
2. **Review and canonical layer:** original preserved; proposal reviewed; member-confirmed Moment and related canonical objects.
3. **Authorized relationship and placement layer:** exact-version references, provenance, lifecycle, audience, purpose, sensitivity, and eligibility.
4. **Focused rooms and projections:** Journal, Story, Work, Projects, Resume, Studio, Slate, Feed, public or permissioned views.
5. **Activation layer:** Use This Moment, practice, manager/update draft, share, export, Project connection, Story selection, next step.
6. **Outcome and learning layer:** completion, usefulness, correction, dismissal, staleness, contradiction, revocation, deletion.
7. **Return-value layer:** finite Home, recent and resurfaced Moment, Then and Now, Replay, source-linked prompt, Focus Theme, future revisit.
8. **New contribution:** the member captures the next Moment because the system made prior contribution useful.

Cross-cutting controls:

- Trusted server identity.
- Authorization before retrieval.
- Private-by-default storage.
- Exact audience preview.
- Canonical/interpretation/projection separation.
- AI proposal and evaluation lifecycle.
- Accessibility and failure parity.
- Privacy-safe telemetry, feature flags, rollout, rollback, and deletion propagation.

## 6.2 Connected-room logical contract

Document the following as a logical contract, not a committed schema:

```text
ResolvedRoomContext
- room_id
- room_role
- viewer_mode
- audience_state
- truth_state
- primary_object_reference
- permitted_source_summary
- authorized_relationships[0..2]
- primary_continuation_action
- secondary_actions[0..2]
- optional_temporal_context
- status_or_limitation_copy
- explanation_or_reason
```

Rules:

- The context resolver receives trusted session identity and route purpose.
- Authorization occurs before data, search, media, cache, or AI retrieval.
- A room may render no connective module when no truthful relationship exists.
- Public mode may use only approved public-safe context.
- Owner mode may use private context only for the current owner.
- Relationship type, audience, source version, lifecycle, and staleness must be explicit.
- The UI cannot infer or broaden relationships from labels or client data.
- Each primary action declares what it uses, what it changes or creates, whether AI is involved, where it is stored, and who can see it.

## 6.3 Candidate relationship types

Preserve as logical vocabulary for Architecture Standard review:

- supports Resume claim
- appears in Story chapter
- belongs to Project
- demonstrates skill in practice
- useful for interview or Moment Lab prompt
- derives from or links to source
- changed from earlier Moment
- influenced outcome
- continues unfinished thread
- appropriate for audience or purpose
- selected as Progress Keepsake

Do not commit all relationship types to schema in the Bible. The Architecture and Data Standard must define which are canonical, placement, projection, interpretation, or operational relationships.

## 6.4 No new system of record

The "proof graph" is not a separate product or database truth. It is the governed relationship and placement capability emerging from the canonical Slate. Make it an explicit acceptance outcome of `PS-PLACEMENT-001` and later connected-view packages.

# 9. Experience-pattern specifications for the Experience System

## 9.1 Slate Spine

Purpose: orient a user inside a focused room without creating another navigation bar.

Required elements:

- Room role in one concise line.
- Viewer/audience or truth label when material.
- Zero to two meaningful relationships.
- One dominant next action.
- Optional status or limitation statement.

Placement:

- Near the hero or primary content header.
- May collapse on mobile into a compact contextual card.
- Must not compete with the room's primary task.

States:

- public approved relationship
- owner private relationship
- no relationship available
- source deleted or unavailable
- action unavailable or Coming later
- browser-local limitation
- restricted audience
- AI unavailable

## 9.2 Resume Backstory Drawer

Use only for three to five anchor claims initially.

Content hierarchy:

1. What the claim says.
2. How it was earned: context, contribution, outcome.
3. Related Project, Story chapter, or approved supporting context.
4. Optional "Practice telling this" action.
5. Source or provenance language appropriate to the audience.

Rules:

- Public-safe only on public Resume.
- No raw private Journal, owner notes, or source files.
- Drawer is progressive depth, not default bulk.
- Practice route must preserve the exact live Studio truth.

## 9.3 Studio Return Ticket

Trigger only after meaningful progress, such as Review or Improve.

Public/browser-local version:

- Primary: reconnect to the approved work behind the answer.
- Secondary: practice a related question.
- Secondary: review the browser-local attempt where current behavior supports it.

Owner future version:

- Save what changed in how I explain this.
- Connect practice to a confirmed Moment or Project.
- Try again later with a source-linked variation.
- Compare with an earlier owner-authorized attempt.

Rules:

- Never interrupt the active answer flow.
- Never claim server persistence in public/browser-local mode.
- Never save, connect, or schedule without explicit member action.

## 9.4 Then and Now

Inputs:

- Two or more authorized, source-linked records.
- A deterministic time or relationship basis.
- Optional AI wording after sources are established.

Output examples:

- Same challenge, different season.
- You described this differently six months ago.
- This explanation contains more specific context than the earlier version.
- An earlier decision contributed to this outcome.

Controls:

- inspect sources
- not related
- too personal
- not useful
- dismiss
- correct relationship
- use this Moment

## 9.5 Focus Themes

A Focus Theme is an optional private overlay, not a destination or identity label.

Examples:

- Explain my work clearly.
- Practice calm confidence.
- Reclaim momentum.
- Prepare for a leadership transition.
- Make technical contribution visible.
- Build toward a chosen learning goal.

It may tune prompts, resurfacing, Replay, Studio question selection, and one next step. It may not silently filter out other history, define the person, or become public without explicit projection.

## 9.6 Progress Keepsakes

A Keepsake is a reference to an existing authorized object or projection.

Candidates:

- Strongest interview clip.
- Exact human sentence.
- Confirmed Resume claim.
- Before-and-now pair.
- Replay Moment.
- Story chapter.
- Meaningful Project outcome.

Rules:

- No copied authoritative text as a new truth.
- No points, rarity, ranking, or public trophy behavior.
- Deleting or revoking the source updates or removes the Keepsake.

# 15. Final governing summary

PeerSlate's hook strategy and architecture strategy are the same strategy:

> Capture something real once. Preserve what is true. Connect it by reference. Use it in a focused room. Return later to see what changed and take one worthwhile next step.
