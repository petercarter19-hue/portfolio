## Visual, accessibility, and truth findings

### Strong evidence worth preserving

- The desktop homepage sequence has a clear dominant object and action.
- The Deep Navy Gold hierarchy is recognizable and professionally composed.
- Voice and Text are both visible.
- The homepage boundaries are unusually clear: fictional example, no visitor
  input, no microphone activation, no AI request, nothing stored, and a normal
  link to the real public Studio.
- The fixed bottom-line-first coaching sequence communicates the intended
  question -> answer -> review -> retry story effectively.
- Homepage JavaScript-unavailable and reduced-motion intent are documented.

These strengths make the archive useful design input for a later separately
activated homepage package after correction. They do not satisfy Gate 2.4.

### Mobile legibility and touch conflict

The source intentionally compresses the experience to fit one viewport rather
than reflowing and allowing readable document flow:

- At the portrait breakpoint, key content drops to roughly 7-10.5 px, mode
  controls are 38 px high, and primary buttons are 40 px high.
- At the 844 x 390 landscape breakpoint, metadata and body copy drop to roughly
  5.5-8 px, controls and primary buttons drop to 27 px high, and the persistent
  truth bar is hidden.

This conflicts with WCAG 2.2 AA intent, the initiative rule not to shrink
content until unreadable, the package's own claim that portrait touch controls
are at least 44 CSS px, and its inventory claim that the truth bar is
persistent. A future revision must stack, disclose, and scroll instead of
shrinking the whole composition.

### Accessibility annotation gap

The 18 state HTML files contain 32 button elements, but the reviewed source has
no button `type` attributes, no interaction roles, no `aria-pressed`, no
`aria-selected`, and no `aria-live` regions. The source is design evidence, not
production code, so this is not treated as an implementation defect. It is
still a Gate 2.4 evidence gap because file `06` requires annotated screen-reader
names/states and processing/error announcements. The self-review defers these
questions to later implementation instead of specifying them for feasibility.

### Authority conflict: written-first versus voice-first

The current repository authority names `PUBLIC-02_ACTIVE_WRITTEN_PRACTICE` and
allocates a focused active written question/answer state. The received
`VOICE_FIRST_INPUT_AUTHORITY_ADDENDUM.md` says it supersedes any Interview Studio
mockup that is written-only or written-default. The archive itself cannot
silently create that owner decision. The designated manager must record an
explicit Pete decision that either:

1. changes the current public Studio to voice-first with Text as a first-class
   peer; or
2. limits voice-first emphasis to the later homepage demonstration while the
   current Studio Gate 2.4 retains its approved written-practice framing.

Until that decision is recorded in the initiative authority, the correction
screens are proposals, not controlling Studio authority.

### Copy and coaching-truth corrections

- Visible homepage copy describes the narrative as moving from "capture, to
  proof, to practice." Current Site Rules deprecate ambiguous user-facing
  "proof" language. Use language such as "capture, to presentation, to
  practice" or another approved phrase.
- The improved retry adds a "repeatable review process for the next phase,"
  which is not established in the fictional original answer. Even a fictional
  coaching demonstration should not model an AI inventing an outcome. Seed the
  fact in the original sample or remove it from the improved retry.
