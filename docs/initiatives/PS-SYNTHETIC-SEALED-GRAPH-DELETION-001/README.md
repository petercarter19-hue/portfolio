## Pinned browser and privacy contract

On the approved Darwin arm64 / Python 3.14 host, the worker validates a local
hash lock for Playwright `1.62.0`, greenlet `3.5.5`, pyee `13.0.1`,
typing-extensions `4.16.0`, and Chromium revision `1234` / browser version
`151.0.7922.34`. It installs only that reviewed closure beneath a run-scoped
root.

Before the first Graph POST, it launches a separate headed probe, validates the
exact executable/version, opens `about:blank`, closes all probe resources, and
proves the probe root removed. It then launches the actual headed browser,
creates exactly four non-persistent no-capture contexts, and proves the
signed-out Workshop private baseline. Playwright runtime modules and paths are
unloaded and the actual root is removed before SQL retirement. Probe and actual
cleanup are aggregated so one cleanup failure does not suppress the other. A
locally started Playwright driver is stopped before runtime release even when
executable validation fails before the provider can return it.

After email submission, each sign-in resolves a document-bound password input
handle without passing a secret, then proves the exact top-level CIAM
authorization origin. Only then does one synchronous browser-side callback
recheck that same document and origin and write the generated password. A
redirect during locator waiting detaches or changes the handle before any
secret crosses the boundary, so the redirected page receives zero password
material. The worker revalidates the exact origin immediately before password
submission; any later redirect stops without submitting the password.

No generated identity, credential, token, caller ID, routing value, Graph
subject, private item key/version/wording, browser state, SQL row, Graph
response, or mutation ledger may leave worker memory. The output is limited to
closed reason codes and allowlisted counts. Python cannot guarantee physical
zeroization of immutable strings; the enforced boundary is removal of the
worker's direct references and no value-bearing file, argument, environment,
log, exception, report, or evidence path.

## Ambiguity and no-retry rule

Every mutation is single-attempt. Before mutation, a mismatch is a closed
refusal. Once an external mutation may have occurred, an unexpected status,
body, redirect, token binding, network result, cleanup result, or partial state
is indeterminate.

If both exact customers exist but a Workshop proof fails, the worker attempts
each known application-item cleanup independently. Proven browser/runtime/root
cleanup permits bounded retirement and Graph-deletion containment of only the
two bound subjects; the operation still returns `indeterminate` and cannot be
reported as accepted. Ambiguous browser cleanup blocks that containment
boundary.

Each create records one finite state: `known_created`,
`ambiguous_maybe_created`, or `known_not_created`. A definitive rejected 4xx,
including 409, never enters reconciliation for that alias. An ambiguous create
permits one bounded exact-filter reconciliation and recoverable containment
pass only; an object is eligible only when the exact generated identity, random
mail marker, full ordinary-customer shape, and operation-local attempt window
all match. Before browser cleanup, that partial-create path may reconcile and
soft-delete an active exact proven subject if safely needed, including an
earlier independently bound subject, then attempt bounded direct active/deleted
state probes. Any ambiguity remains indeterminate. An exact subject already
found in deleted items remains unpurged. The path
independently attempts session cleanup, never repeats a POST, never lists
unrelated identities, and never purges a deleted item. Irreversible purge is
allowed only on the full exact-pair path after browser/runtime/root cleanup is
proven and exact-two SQL retirement has committed. Graph deletion has a finite
in-memory per-alias phase ledger; permanent deletion is additionally gated on
both exact soft deletes and all four soft-state proofs. There is no blind replay
of customer creation, Workshop mutation, SQL retirement, soft deletion, purge,
or the full operation. Further read-only reconciliation requires separate
authority for the exact attempted pair.
